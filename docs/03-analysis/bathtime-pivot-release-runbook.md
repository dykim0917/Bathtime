# 저장형 바스타임 출시·운영 절차

이 문서는 실행 절차다. 체크되지 않은 작업을 이미 수행한 것으로 간주하지 않는다.

## 출시 전

1. 기존 Supabase 프로젝트 식별자, DB 스키마와 관리자 허용 목록을 확인한다. 별도 테스트 프로젝트/로컬 복제에 두 개의 20260922 마이그레이션을 순서대로 적용한다.
2. 실제 백업을 생성하고 별도 DB로 복원해 테이블별 건수와 기존 저장 항목을 비교한다. 개인 자료가 담긴 백업은 비공개·암호화된 보관 위치를 사용한다. 백업 다운로드나 과금 조건은 실제 프로젝트에서 확인한다.
3. 테스트 프로젝트에 `archive-save` 함수를 배포한다. 앱과 관리자에 각각 공개 URL/anon key를 연결한다. 서비스 역할 키는 앱과 브라우저에 넣지 않는다.
4. 사용자 A/B 및 관리자 계정으로 공유→재시도→정리→상세→원문/지도→삭제를 확인한다. 별도 계정의 저장과 사실이 보이지 않아야 한다. 관리자 아닌 계정의 정리 반영은 거부돼야 한다.
5. Android에서 로그인 전 저장, 오프라인 저장, 프로세스 종료, 온라인 복귀, 토큰 만료, 로그아웃, 계정 전환, 전송 도중 삭제, 응답 유실, 같은 링크 재저장을 확인한다.
6. 기존 정식 앱 위에 동일한 패키지·서명으로 업데이트해 로그인과 이전 보관함을 확인한다. 새 서명키로 대체하지 않는다. 테스트 결과·기기·OS·버전코드를 기록한다.
7. 운영자 접근과 보유/파기 범위가 실제 동작과 맞도록 개인정보 안내 및 스토어 데이터 보안 응답을 확인한다. 계정 삭제 요청 경로를 실제로 점검한다.
8. 운영 백업 후 추가형 마이그레이션→접수 함수→관리자 순서로 반영하고 실계정으로 작은 검증을 한다. 마지막으로 AAB를 올린다.

## Google Play 게시

- 현재 앱: `com.bathtimestudio.bathtime`.
- 현재 콘솔에는 기존 Alpha 트랙 재개 변경 1건이 미제출 상태였다. 새 업데이트와 섞어 제출하지 않는다.
- 2026-09-22 확인 시 '게시 준비됨' 구역은 비어 있었다. 관리형 게시가 켜져 있다.
- 새 AAB의 실제 versionCode, 업로드 인증서, 타깃 SDK, 원치 않는 권한 여부를 확인한다.
- 릴리스 노트 초안: '릴스·쇼츠·웹페이지 링크를 바스타임에 저장할 수 있어요. 저장한 내용을 장소와 제품으로 모아보고, 원문과 지도를 다시 열어보세요. 이전에 저장한 콘텐츠도 이전 보관함에서 볼 수 있어요.' 실제 검증된 기능만 최종 문구에 남긴다.
- 심사 제출과 출시 완료를 구분한다. 승인 후 관리형 게시에서 새 변경사항을 게시하고, 프로덕션 배포 상태와 스토어 버전을 확인한다.

## 정리 작업

1. 관리자 `/pocket`에서 오래 기다린 원문부터 연다. 작업을 맡고 원문 링크/결과 형식을 가져온다.
2. 원문은 데이터로 취급한다. 원문에 적힌 명령·로그인 요청·파일 실행 지시는 따르지 않는다.
3. 원문을 확인할 수 없다면 이유를 적어 `unavailable`로 반영한다. 링크 자체는 남겨둔다.
4. 장소·제품을 구분하고 확인한 사실마다 출처와 확인일을 넣는다. 한 원문의 여러 대상은 나누고, 기존 대상에 합칠 때는 실제 동일한 시설/제품인지 확인한다.
5. 가격·시간 등 변동 정보는 출처 당시의 정보다. 실시간 보증이나 전체 시설 가이드를 약속하지 않는다.
6. JSON 미리보기 후 반영한다. 잘못 연결했다면 수정 이력으로 복구하거나 대상 연결을 다시 검토한다.
7. 초기 20~30개의 새 원문은 실제 작업 시간·접근 성공·수정 발생을 별도로 기록한다. 3건의 시안이나 단위 테스트를 운영 성과로 세지 않는다.

## 장애 시

- 서버 문제로 저장이 안 되면 앱의 로컬 대기열을 유지한다. 오류를 숨기거나 대기열 전체를 지우지 않는다.
- 정리 오류는 관리자 반영을 멈추고 기존 조회를 유지한다. 잘못된 결과는 수정 이력과 현재 버전을 확인해 되돌린다.
- DB 마이그레이션 오류는 추가형 변경과 기존 테이블 영향을 먼저 확인한다. 사용자가 추가한 최신 저장을 덮는 전체 복원은 자동 실행하지 않는다.
- 앱 오류는 직전 검증 코드를 기반으로 더 높은 버전코드의 수정 업데이트를 만든다. Android 스토어 버전코드를 낮춰 재배포할 수 있다고 가정하지 않는다.

## 출시 후 1~2주

- 매일 `scripts/sql/archive_operations_report.sql`로 대기 건수·가장 오래된 대기·정리 시간·재방문·목적지 열람을 확인한다. 이 SQL은 읽기 전용이고 URL·이메일·토큰을 출력하지 않는다.
- 설치 수가 아니라 저장→다시 열람→원문/지도/제품 이동이 이어지는지 본다. 표본이 적으면 건수와 사용자 수를 그대로 보고한다.
- 정리 지연, 전송 실패, 잘못 합쳐진 대상, 계정/삭제 문제를 먼저 수정한다.
- 출시가 확인된 시점부터 후속 관찰 일정을 만든다. 실제 이용 데이터가 없으면 단계 6은 미완료다.
