# 바스타임 개발 문서: 판정 모델 기반 온천 상세·카드 개편

온천 숙소와 시설을 `좋다/나쁘다`로 추천하는 대신, 이용 경험과 공식 정보를 읽고 바스타임의 기준으로 판정하는 모델을 데이터 구조와 UI에 반영하기 위한 개발 명세입니다.

카피 규칙은 [바스타임 판정문 작성 규칙](../../03-content/onsen-judgment-copy-guide.md), 용어 표기는 [온천 용어 가이드](../../03-content/onsen-term-guide.md)를 따릅니다. 지역별 DB seed 운영은 [온천 숙소 지역별 DB Seed 프로세스](../../04-report/onsen-regional-db-seed-process.md)를 따릅니다. 본 문서는 그 규칙을 담는 스키마, 컴포넌트, 상태, QA 기준을 정의합니다.

적용 범위:

- 온천 상세 페이지: `/onsen/[slug]`
- 검색 결과 카드: `/onsen/results`
- 홈 검색 제안, 인기 검색어, 주요 필터
- 관리자 온천 데이터 입력/검수 화면

## 1. 모델 목표

바스타임의 온천 검색기는 숙소 홍보 문구나 이용 경험 원문을 전달하지 않습니다. 대신 다음 질문에 답합니다.

- 이곳은 어떤 온천 경험이 중심인가?
- 객실 내 프라이빗탕, 대절탕, 대욕장, 온천수 방식은 어떻게 구분해야 하는가?
- 계절, 예약 조건, 수온, 벌레, 혼잡처럼 선택 전에 알아야 할 변수는 무엇인가?
- 그 판단은 몇 건의 이용 경험과 어떤 플랫폼 표면을 바탕으로 하는가?

사용자에게 보여줄 핵심 가치는 `판정`입니다. 내부적으로 수집·태깅·집계 과정에서 `signal`이라는 단어를 쓰더라도, 사용자 노출 UI에서는 `신호`라는 표현을 쓰지 않습니다.

## 2. 데이터 모델

### 2.1 신규: `verdict`

숙소 또는 시설 1건당 `verdict` 1건을 둡니다. 구현 방식은 별도 테이블을 우선 검토하고, 초기 마이그레이션 속도가 중요하면 JSONB 컬럼으로 시작할 수 있습니다.

```jsonc
{
  "target_id": "hakone-byakudan",
  "target_type": "accommodation",
  "level": "full",
  "headline": "객실 안에서 온천이 완결되는 숙소입니다. 대신 수온은 계절을 탑니다.",
  "briefing": {
    "experiences_read": 342,
    "onsen_related": 234,
    "platforms": ["jalan", "rakuten", "google_maps", "tripadvisor"]
  },
  "items": [
    {
      "order": 1,
      "type": "positive",
      "headline": "객실 노천탕 만족은 논쟁이 없는 항목입니다.",
      "counts": {
        "mentions": 187,
        "negative": 4,
        "denominator": "onsen_related",
        "platform_count": 3,
        "direction_counts": {
          "positive": 171,
          "mixed": 12,
          "negative": 4,
          "neutral": 0
        }
      },
      "body": "프라이버시와 독립성에 대한 평가는 플랫폼을 가리지 않고 일관됩니다.",
      "verdict": "대욕장 없이 객실탕만으로 충분한지 고민하지 않으셔도 되는 구조입니다.",
      "chip_label": "객실탕 중심",
      "season_months": null
    }
  ],
  "verified_at": "2026-07-01",
  "status": "published"
}
```

필드 원칙:

- `headline`: 카드와 상세에서 함께 쓰는 단일 대표 판정문입니다.
- `briefing.experiences_read`: 직접 읽은 이용 경험 수입니다. 플랫폼 노출 수와 혼용하지 않습니다.
- `briefing.onsen_related`: 직접 읽은 이용 경험 중 온천 관련으로 분류한 수입니다.
- `briefing.platforms`: 실명 플랫폼 코드입니다. 최소 1개 이상이어야 합니다.
- `items`: 사용자에게 노출되는 판정 항목입니다. 내부 태깅 결과를 그대로 노출하지 않습니다.
- `items[].type`: `positive | conditional | minor` 중 하나입니다.
- `items[].counts.mentions`: 필수입니다. 숫자가 없으면 해당 판정 항목을 게시하지 않습니다.
- `items[].counts.negative`: 필수입니다. 부정값이 없으면 `0`으로 저장합니다.
- `items[].counts.platform_count`: 필수입니다. 해당 항목이 확인된 독립 직접 본문 플랫폼 수입니다.
- `items[].counts.direction_counts`: 필수입니다. `positive`, `mixed`, `negative`, `neutral`을 모두 숫자로 저장합니다.
- `items[].chip_label`: 카드에 축약 노출할 명사형 라벨입니다.
- `season_months`: 계절성 항목일 때만 `[11, 12, 1, 2, 3]`처럼 저장합니다.

### 2.2 `level`: full / lite

초기 공급 속도와 품질 게이트를 함께 잡기 위해 판정 레벨을 나눕니다.

| level | 조건 | 사용자 노출 |
| --- | --- | --- |
| `full` | 직접 읽은 이용 경험 300건 이상, 온천 관련 200건 이상, 직접 본문 플랫폼 3개 이상, 채택 기준을 통과한 판정 항목 3개 이상 | 상세 판정 블록 전체 노출 |
| `lite` | 구조 사실 기반 대표문과 수집 브리핑은 있으나 full 표본 기준 또는 판정 항목 기준 미달 | 카드와 상세 상단에 간략 정보만 노출 |
| `draft` | 수치나 문장 검수 미완료 | 공개 페이지에서는 기존 기본 정보 폴백 |

`full`만 고집하면 데이터 생산 속도가 지나치게 느려질 수 있습니다. 초기에는 `lite`로 공개 가능한 범위를 만들고, 핵심 숙소부터 `full`로 승격합니다.

`lite`의 `headline`은 확인된 구조 사실만 서술합니다. 집계 해석형 단정은 `full` 전용입니다.

허용:

```text
전 객실 노천탕 구조의 숙소입니다.
대욕장과 대절탕을 함께 볼 수 있는 숙소입니다.
```

금지:

```text
객실 노천탕 만족이 일관됩니다.
수온은 계절을 탑니다.
대욕장 없이도 충분한 숙소입니다.
```

위 금지 예시는 이용 경험 집계와 판정 항목의 counts가 있어야 성립하는 문장입니다. `lite`에서 이런 문장이 필요하면 먼저 `full`로 승격합니다.

### 2.3 게시 게이트

서버 검증, DB constraint, 업로드 스크립트 중 최소 하나에서 아래 조건을 강제합니다.

`published full` 조건:

- `briefing.experiences_read >= 300`
- `briefing.onsen_related >= 200`
- `briefing.platforms.length >= 3`
- `items.length >= 3`
- 모든 `items[].counts.mentions`가 null이 아니고 0 이상
- 모든 `items[].counts.negative`가 null이 아니고 0 이상
- 모든 `items[].counts.platform_count >= 2`
- 모든 `items[].counts.direction_counts`가 `positive`, `mixed`, `negative`, `neutral` 숫자를 가짐
- 모든 판정 항목의 `mentions`가 `10건 이상`이면서 해당 분모의 `2% 이상`
- `headline`과 `items[].headline/body/verdict`에 금지 패턴 없음

`published lite` 조건:

- `headline` 있음
- `briefing.experiences_read` 있음
- `briefing.platforms.length >= 1`
- `items.length`는 0~2개 허용
- full 표본 기준 또는 판정 항목 채택 기준을 충족하지 못한 항목은 독립 판정 근거로 노출하지 않음
- `headline`은 구조 사실 기반 문장만 허용
- 집계 해석형 단정문은 사용 불가
- 화면에는 `판정 항목 N개`처럼 부풀려 보이는 표현을 쓰지 않음

금지 패턴 예:

```text
후기에 따르면|리뷰에서 말하길|~라는 후기|많더라|종종|대체로|인 편입니다|일 수 있습니다|로 보입니다
```

`[N]` 처리:

- 카운트 미확정 항목은 DB에 넣지 않습니다.
- 프론트에는 `[N]` 렌더링 경로를 만들지 않습니다.

### 2.3.1 판정 항목 채택 규칙

`full`의 3개 이상 판정 항목은 아무 내부 태그나 올린 개수가 아닙니다. 각 항목은 [바스타임 판정문 작성 규칙](../../03-content/onsen-judgment-copy-guide.md)의 v0.1 채택 기준을 통과해야 합니다.

항목별 필수 집계:

```jsonc
{
  "signal_key": "room_open_air_bath_experience",
  "bath_area": "room_open_air_bath",
  "counts": {
    "mentions": 127,
    "negative": 3,
    "denominator": "onsen_related",
    "platform_count": 3,
    "direction_counts": {
      "positive": 118,
      "mixed": 6,
      "negative": 3,
      "neutral": 0
    }
  },
  "adoption_status": "verdict_basis"
}
```

`adoption_status` 값:

| status | 의미 | 공개 처리 |
| --- | --- | --- |
| `verdict_basis` | 10건 이상, 분모 2% 이상, 2플랫폼 이상 | `items[]`로 사용 가능 |
| `attention_note` | 5건 이상, 2플랫폼 이상이나 `verdict_basis` 미달 | 독립 근거로 세지 않고 보조 주의 문장만 가능 |
| `internal_only` | 1~4건 또는 단일 플랫폼 | 사용자 노출 금지 |

예를 들어 `유량 주의 4건 / 1플랫폼`은 `internal_only`입니다. 이것을 full verdict의 독립 근거로 올리면 안 됩니다.

방향성 기준:

- `mentions = positive + mixed + negative`
- `negative = negative`
- `neutral`은 시설 존재나 객실명 확인에는 쓸 수 있지만 만족/불만 판정 언급 수에는 넣지 않습니다.
- `mixed`는 부정값으로 합치지 않고 조건부 해석에 사용합니다.

### 2.4 신규: `fact_status`

온천 정보 항목은 `확인 필요 / 조건 확인` 같은 단독 라벨을 폐기하고 3상태로 관리합니다.

| status | 의미 | UI 표기 |
| --- | --- | --- |
| `confirmed_yes` | 있음 또는 해당 항목 확인 | 값 그대로 표기 |
| `confirmed_no` | 없음 확인 | `없음 — {대체 구조 설명}` |
| `check_at_booking` | 확인했으나 예약 조건에 따라 달라짐 | `예약 시 확인: {무엇을} — {어디서}` |

예:

```jsonc
{
  "facility": "private_bath",
  "status": "check_at_booking",
  "check_what": "가온 가능 여부",
  "check_how": "예약 시 숙소 문의"
}
```

금지:

- `확인 필요`
- `확인 중`
- `조건 확인`
- 라벨 없는 `미확인`

`check_at_booking`은 반드시 `check_what`과 `check_how`를 함께 저장합니다.

### 2.5 지역 데이터 정규화

지역 표기에는 한국어 컬럼만 사용합니다.

필수 컬럼:

- `country_name_ko`
- `region_group_name_ko`
- `prefecture_name_ko`
- `onsen_area_name_ko`
- `city_name_ko` 또는 `municipality_name_ko`

렌더링 규칙:

- 기본 표기: `권역 · 현 · 온천지`
- 같은 계층명이 반복되면 한 번만 표시합니다.
- 로마자 내부 코드(`kumamoto`, `kurokawa`, `saga`, `takeo`, `beppu`)는 화면에 노출하지 않습니다.

예:

- `규슈 · 구마모토현 · 구로카와`
- `규슈 · 사가현 · 다케오`
- `규슈 · 오이타현 · 벳푸`
- `간토 · 가나가와현 · 하코네`
- `홋카이도 · 조잔케이`

## 3. 상세 페이지 명세

### 3.1 섹션 순서

1. 헤더: 숙소명, 한국어 지역명, 핵심 배지
2. 바스타임 판정 블록
3. 온천 정보
4. 이럴 때 맞아요
5. 기본 정보 / 접근
6. 제휴 또는 가격 확인 CTA

기존 `이런 점이 좋았어요`, `AI 요약`, `후기 신호` 성격의 섹션은 판정 블록으로 대체합니다. 두 섹션이 공존하면 바스타임의 단일 화자 원칙이 깨집니다.

리뷰 쓰기 기능은 트래픽 확보 후 재도입합니다. 지금 단계에서는 빈 UGC 공간보다 바스타임 판정의 신뢰도가 더 중요합니다.

### 3.2 판정 블록

```text
┌─────────────────────────────────────────┐
│ 바스타임 판정                    기준일 2026.07 │
│ 객실 안에서 온천이 완결되는 숙소입니다.          │
│ 대신 수온은 계절을 탑니다.                    │
│─────────────────────────────────────────│
│ 수집 브리핑                               │
│ 직접 읽은 이용 경험 342건 · 온천 관련 234건   │
│ 확인 플랫폼: 자란 · 라쿠텐 · 구글 지도        │
│─────────────────────────────────────────│
│ 근거 1  객실 노천탕 만족은 논쟁이 없는 항목입니다. │
│ 근거 2  겨울 수온은 조건부입니다.              │
│ 근거 3  여름 벌레 유입은 소수 반복 변수입니다.   │
└─────────────────────────────────────────┘
```

규칙:

- 수집 브리핑은 판정 항목보다 위에 둡니다.
- `positive`, `conditional`, `minor`는 아이콘, 좌측 라인, 라벨로 구분합니다. 색상만으로 구분하지 않습니다.
- 판정 항목은 화면에서 `근거 1`, `근거 2`, `근거 3`으로 표기합니다. 대표 블록 제목은 `바스타임 판정`, 카드 스탬프는 `판정 근거 N개`이므로 같은 단어가 세 위계에서 반복되지 않게 합니다.
- 판정 항목 내부 구조는 `헤드라인 → 집계 라인 → 해석 → 결론` 순서입니다.
- 항목 내 결론 프리픽스는 `결론:` 또는 `예약 전 판단:`을 사용합니다. `바스타임 판정:`을 반복하지 않습니다.
- 집계 숫자는 `items[].counts`에서 렌더링합니다. 본문 텍스트에 하드코딩하지 않습니다.
- `season_months`가 현재 월에 해당하면 해당 항목을 상단에 고정하거나 강조할 수 있습니다.
- 사용자 노출 문구에 `신호`를 쓰지 않습니다.

### 3.3 헤더 배지

- 온천수 방식 배지는 1개만 노출합니다.
- `직수 온천`과 `재사용 온천(순환식)`은 동시에 노출하지 않습니다.
- 조어 배지에는 정보 아이콘과 설명을 붙입니다.
- `확인 중` 같은 무라벨 배지는 제거합니다.
- 검수 상태는 `기준일 YYYY.MM`로 대체합니다.

## 4. 검색 결과 카드 명세

### 4.1 카드 구조

```text
┌─────────────────────────────────────────┐
│ [이미지 또는 지역 플레이스홀더]                │
│ 숙소명                        직수 온천 ⓘ  │
│ 간토 · 가나가와현 · 하코네                  │
│─────────────────────────────────────────│
│ 객실 안에서 온천이 완결되는 숙소입니다.          │
│ 이용 경험 342건 분석 · 판정 근거 3개          │
│─────────────────────────────────────────│
│ 겨울 수온 조건부                            │
└─────────────────────────────────────────┘
```

규칙:

- 카드 본문은 `verdict.headline`을 재사용합니다.
- 카드용 요약문을 따로 만들지 않습니다.
- 근거 스탬프는 `이용 경험 {experiences_read}건 분석 · 판정 근거 {items.length}개`로 표기합니다.
- `lite` 판정은 `이용 경험 N건 분석`까지만 표시하고 `판정 근거 N개`는 숨깁니다.
- 조건부 칩은 `items[].type === conditional`의 `chip_label`을 사용합니다.
- `draft`는 `판정 준비 중`으로 표시하고 근거 스탬프를 숨깁니다.
- 리스트 정렬은 `published full` → `published lite` → `draft` 순서를 기본으로 합니다.
- 플랫폼명은 UI 라벨 매핑을 거친 한국어 표기를 사용합니다. 예: `google_maps` → `구글 지도`, `tripadvisor` → `트립어드바이저`.

### 4.2 정렬과 필터

추가 정렬:

- `근거 많은 순`: `briefing.experiences_read desc`
- `온천 관련 많은 순`: `briefing.onsen_related desc`
- `최근 검수순`: `verified_at desc`

필터 정리:

- `방식: 료칸 숙박`처럼 현재 데이터가 모두 같은 단일 옵션은 숨깁니다.
- `겨울 주의` 같은 주의성 필터는 상단 필터에서 제거하고 카드 조건부 칩으로 이동합니다.
- 탕 구성 필터는 코드 매핑 테이블을 참조합니다.
- 필터명과 카드 라벨이 같은 코드를 보도록 해 표기 어긋남을 막습니다.

## 5. `100% 천연온천` 위계 처리

`100% 천연온천`은 공식 근거 없이 쓰면 마케팅 문구처럼 보일 수 있습니다. 바스타임에서는 `직수 온천`을 상위 판단 축으로 둡니다.

권장안:

- `100% 천연온천` 필터를 독립 옵션으로 두지 않습니다.
- 홈 인기 검색어와 추천 검색어에서도 `100% 천연온천`을 제거합니다.
- 필요한 경우 `직수 온천 료칸` 또는 공식 근거가 있는 `원천 100% 직수`로 교체합니다.
- 공식 데이터로 확인된 경우에만 `원천 100%`를 온천 정보 항목에 표시합니다.
- 상단 배지에는 `직수 온천`을 우선 노출합니다.
- 배지 또는 툴팁에 지역 희소성 카운터를 붙일 수 있습니다.

예:

```text
이 지역 42곳 중 직수 온천 확인 7곳
```

### 2.5 글로벌 확장 준비 필드

글로벌 출시는 한국어 판정 모델이 먼저 검증된 뒤 진행합니다. 다만 지금부터 스키마는 언어와 시장을 분리해 둡니다.

`onsen_verdicts.localized_copy`

- 선택 JSONB 필드입니다.
- `ko`, `en`처럼 locale 키를 둡니다.
- `headline`, `items[].headline/body/verdict/chip_label` 같은 문장 레이어만 넣습니다.
- `briefing`, `items[].counts`, `fact_statuses`는 복제하지 않습니다. 카운트와 구조화 팩트는 언어 중립 canonical 데이터로 유지합니다.

`onsen_accommodations.global_travel_facts`

- 선택 JSONB 필드입니다.
- 한국어 MVP에는 당장 노출하지 않더라도 영어권 파일럿에서 필요한 여행자 질문을 담습니다.
- 권장 키는 `tattoo_policy`, `gender_policy`, `english_support`, `couple_private_bath`입니다.
- 값에는 `status`, `label_ko`, `label_en`, `source`, `updated_at`을 둡니다.
- 원문 이용 경험이나 의역 문장은 넣지 않습니다.

상세 기준은 [온천 검색기 글로벌 확장 준비 메모](../../03-content/onsen-global-readiness.md)를 따릅니다.

## 6. 관리자 입력 명세

관리자 화면은 사람이 문장을 자유 입력하는 곳이 아니라, 판정 데이터를 안전하게 입력하고 검수하는 곳이어야 합니다.

필수 입력:

- 대표 판정문
- 수집 브리핑
- 판정 항목
- 각 항목의 mentions / negative / denominator
- 기준일
- 상태: `draft | published`

플랫폼 UI 라벨 매핑:

| 코드 | UI 라벨 |
| --- | --- |
| `jalan` | 자란 |
| `rakuten` | 라쿠텐 |
| `google_maps` | 구글 지도 |
| `tripadvisor` | 트립어드바이저 |
| `agoda` | 아고다 |
| `yahoo_travel` | 야후 트래블 |

관리자 경고:

- 금지 패턴 포함
- 숫자 누락
- 플랫폼 누락
- `신호`, `후기 신호`, `많더라`, `대체로` 등 사용자 노출 금지어 포함
- `객실탕`처럼 용어 가이드상 분리 필요한 표현 포함

권장 UI:

- 판정 항목은 반복 카드로 입력합니다.
- counts는 숫자 input으로 제한합니다.
- denominator는 select로 제한합니다.
- type은 segmented control로 둡니다.
- preview에서 사용자 노출 문구를 바로 확인합니다.

## 7. 마이그레이션 계획

기존 55곳 기준으로 진행합니다.

| 단계 | 작업 | 산출물 |
| --- | --- | --- |
| 1 | `verdict` 스키마 생성과 게시 게이트 구현 | 테이블/컬럼, 업로드 검증 |
| 2 | 지역 `name_ko` 정규화와 용어 코드 매핑 | 데이터 패치 |

| 4 | 상세 페이지 판정 블록과 카드 개편 | 프론트 |
| 5 | 핵심 숙소부터 `lite` 또는 `full` 판정 작성 | 지역 배치 |
| 6 | 기존 `full` 판정의 `platform_count`와 `direction_counts` 백필 | 새 게시 게이트 적용 준비 |
| 7 | `fact_status` 3상태 소급 적용 | `확인 필요` 제거 |

| 10 | 지역별 1차/2차/3차-A/3차-B seed 프로세스 적용 | 지역 간 DB 적재 품질 일관화 |

추천 파일럿 순서:

1. 하코네 또는 유후인 대표 숙소 1곳
2. 객실 내 프라이빗탕 중심 숙소 1곳
3. 대욕장 중심 숙소 1곳
4. 대절탕 중심 숙소 1곳

판정 유형별 표준 케이스를 먼저 만들고 나머지 숙소에 확산합니다.

지역 배치는 한 번에 전량 적재하지 않습니다. 먼저 `full_verdict_candidate`와 `ready_for_db_lite`를 1차로 적재하고, 이후 `needs_platform_reconciliation`/`needs_count_reconciliation` 중 방향값이 안정적인 후보를 2차로 회수합니다. `needs_direction_backfill`은 명시 방향 컬럼이 있는 3차-A와 별도 backfilled CSV가 필요한 3차-B로 분리합니다. 자세한 운영 절차는 [지역별 DB Seed 프로세스](../../04-report/onsen-regional-db-seed-process.md)를 기준으로 삼습니다.
