# 온천시설 판정 데이터 파이프라인

숙소가 아닌 당일입욕 온천시설의 직접 이용 경험을 `onsen_verdicts.target_type = 'facility'` 판정으로 바꾸는 기준입니다. 원천 데이터의 역할은 [온천시설 데이터 모델](./onsen-facility-data-model.md)을 따릅니다.

## 판정 단위

시설 판정은 숙박 만족도가 아니라 아래 세 축을 다룹니다.

1. 핵심 목욕 경험: 물의 감촉, 온천감, 탕 구성, 역사적 목욕 공간, 가족탕·모래찜질 같은 시설 고유 경험
2. 운영 마찰: 혼잡·대기, 예약·입장 방식, 요금·결제, 접근성, 청결·비품, 운영 변동
3. 이용 범위: 당일입욕 대상 욕장, 숙박 공용탕과의 분리, 성별·연령·문신 등 이용 조건

공식 운영 사실과 직접 이용 경험 집계는 판정 안에서도 분리합니다. 공식 필터 사실은 `fact_statuses`와 브리핑에만 쓰고, 후기 언급 수로 바꾸지 않습니다. 물의 감촉과 색은 이용 경험으로 집계할 수 있지만, 직수·순환식 같은 온천수 방식 판정에는 사용하지 않습니다.

## 공개 등급

| 등급 | 시설 표본 기준 | 근거 항목 기준 | 공개 상태 |
| --- | --- | --- | --- |
| `full` | 시설 관련 직접 판독 300건 이상, 직접 본문 플랫폼 3개 이상 | 서로 다른 항목 3개 이상 | `published` |
| `lite` | 시설 관련 직접 판독 50건 이상, 직접 본문 플랫폼 2개 이상 | 서로 다른 항목 2개 | `published` |
| `draft` | 위 기준 미달, D등급, 단일 플랫폼, 범위 분리 필요 | 내부 QA용으로만 보존 | `draft` |

`scope_split`, `hold`, `cleanup_status = split_needed`인 시설은 표본 수와 관계없이 공개 판정을 만들지 않습니다. 당일입욕 전용 표본과 숙박 공용탕 보조 표본의 분리가 끝난 뒤 다시 판정합니다.

## 근거 항목 채택

각 항목은 `onsen_facility_review_signals`의 한 시설 영역과 한 신호 유형을 기준으로 채택합니다. 같은 사람이 같은 항목을 여러 번 언급해도 독립 이용 경험 수를 부풀리지 않도록 `source_count`를 사용자용 `mentions`로 사용하고, 원시 `mention_count`는 `raw_mention_count`로 보존합니다.

- `full`: 독립 이용 경험 10건 이상, 전체 분모의 2% 이상, 2개 이상 플랫폼
- `lite`: 독립 이용 경험 5건 이상, 전체 분모의 2% 이상, 2개 이상 플랫폼
- `neutral`, `insufficient`, 단일 플랫폼 항목은 공개 판정에서 제외
- 같은 신호 유형이 여러 시설 영역에 있으면 가장 강한 한 영역만 대표 근거로 채택
- `positive`, `mixed`, `negative`를 합쳐서 긍정 수처럼 쓰지 않고 방향별 카운트를 보존

분모는 항상 `briefing.experiences_read = facility_related_direct_reviews`입니다. 플랫폼에 보이는 후기 수, 검색 스니펫, AI·OTA 요약은 분모와 항목 수 어디에도 넣지 않습니다.

## 시설 유형별 우선순위

| 시설 유형 | 먼저 보는 핵심 경험 | 함께 보는 운영 조건 |
| --- | --- | --- |
| 역사적 공중탕 | 역사적 목욕 공간, 온천감, 물의 감촉 | 이용 범위, 접근성, 비품 |
| 대형 당일온천·웰니스 | 탕 구성, 청결·비품, 사우나·휴게 경험 | 혼잡·대기, 요금·결제 |
| 가족탕·대절탕 | 가족탕·대절탕 경험 | 예약 방식, 요금, 이용 대상 |
| 모래찜질·증기탕 | 특화 목욕 경험 | 대기, 복장·이용 범위, 접근성 |

시설 유형 우선순위는 어떤 항목을 먼저 보여줄지 정할 뿐, 임계값을 낮추지는 않습니다.

## 생성과 적재

```bash
node scripts/build_onsen_facility_verdict_pipeline.mjs
node scripts/build_onsen_facility_verdict_pipeline.mjs --apply
```

스크립트는 활성 시설의 최신 증거 회차만 읽고 JSON, CSV, Markdown QA 리포트, 재현 가능한 upsert SQL을 만듭니다. `--apply`는 19개 시설의 공개·내부 판정을 함께 upsert한 뒤 DB 값을 다시 읽어 수와 상태를 검증합니다.

## QA 체크리스트

- [ ] visible review pool과 직접 판독 분모를 합치지 않았는가?
- [ ] `source_count`가 분모를 넘지 않는가?
- [ ] 공개 항목이 2개 이상 플랫폼과 2% 기준을 통과하는가?
- [ ] 혼합 방향을 부정 0건으로 숨기지 않고 `direction_counts.mixed`에 보존했는가?
- [ ] 범위 분리 시설이 `published`로 올라가지 않았는가?
- [ ] 공식 필터 사실이 후기 언급 수로 변환되지 않았는가?
- [ ] 후기의 감촉·색 표현을 온천수 방식 근거로 쓰지 않았는가?
