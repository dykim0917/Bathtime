# 온천시설 수집 후 QA 피드백

규슈 12곳과 간사이·산인·세토우치 5곳의 수집 원장을 정규화하고, 시설 판정을 생성해 DB에 적재한 뒤 확인한 개선 사항입니다. 다음 지역 수집부터는 이 문서를 사전 체크리스트로 사용합니다.

## 1. 이번 결과

- 시설 17곳을 정규화했습니다.
- 직접 읽은 시설 이용 경험은 2,440건입니다.
- 판정은 `full` 2곳, `lite` 12곳, `draft` 3곳입니다.
- 후기 신호는 193건입니다.
- 공식 필터 사실은 21건이지만, 타이코노유 15건과 도고온천 본관 6건에만 집중됐습니다.
- 공식 수질 사실은 16건입니다.
- 바로 공개할 수 있는 온천수 방식 배지는 0건입니다.
- 감촉 신호 행은 있었지만, 구체적인 감촉 코드와 공식 수질 후보를 안정적으로 연결할 수 없어 감촉 필터는 모두 보류했습니다.
- 공식 백탁 원문과 범위가 함께 확인된 운젠 고지옥 온천관 1곳만 색 필터를 공개할 수 있었습니다.

수집량 자체는 판정 생성에 충분한 편이었습니다. 다음 개선의 핵심은 더 많은 리뷰를 무조건 읽는 것이 아니라, 판정과 필터로 전환할 수 있는 구조로 읽는 것입니다.

## 2. 유지해야 할 점

다음 항목은 이번 수집에서 잘 지켜졌으며 이후에도 바꾸지 않습니다.

- 플랫폼 노출 리뷰 수와 직접 읽은 리뷰 수를 분리합니다.
- 검색 스니펫, 토픽 칩, AI 요약, OTA 요약은 직접 판독 분모에 넣지 않습니다.
- 직접 판독 수는 개별 원장 행으로 재현합니다.
- 공식 사실과 후기 신호를 분리합니다.
- 시설과 숙소를 별도 모델로 유지합니다.
- 최신 리뷰와 저평점 리뷰를 포함해 여러 층위를 읽습니다.
- 시설 영역을 `public_bath`, `family_bath`, `sand_bath`, `steam_bath`, `facility_wide` 등으로 나눕니다.
- 후기의 `かけ流し`, 원천감, 염소 냄새를 온천수 방식 확정 근거로 사용하지 않습니다.

## 3. 다음 수집 전 필수 수정

### 3.1 canonical 원장은 하나만 남깁니다

기본 원장과 보강 원장이 같은 디렉터리에 함께 있으면 QA 단계에서 두 파일을 동시에 읽을 위험이 있습니다.

- 최종 보강 원장은 파일명에 `_integrated_`를 사용합니다.
- 시설별 최종 QA에는 실제로 사용한 원장 경로를 기록합니다.
- 집계와 signal rows는 반드시 같은 canonical 원장에서 생성합니다.
- 기본 원장은 삭제하지 않아도 되지만, 최종 집계 입력으로 다시 사용하지 않습니다.
- 플랫폼별 직접 본문 수는 별도 보고값을 믿지 않고 canonical 원장에서 재계산합니다.

### 3.2 원장 값의 표현을 통일합니다

이번 원장에는 `content_type=platform_review`, `direct_review`, `review`와 `direct_body_status=full`, `complete`가 혼재했습니다. 정규화 과정에서 흡수할 수는 있지만, 다음 수집부터는 아래 값만 사용합니다.

- `content_type`: `platform_review`, `blog_context`, `activity_post`, `snippet`
- `direct_body_status`: `full`, `partial`, `not_available`
- `review_count_eligible`: `true`, `false`
- `facility_related`: `true`, `false`
- `scope_bucket`: 시설 모델에 맞는 허용값만 사용

`content_type`으로 실제 이용 여부를 표현하지 않습니다. 리뷰를 읽었지만 실제 입욕하지 않은 경우는 짧은 paraphrase와 `access_note`에 `did_not_use`를 명시하고, QA 집계 전에 별도 제외 목록을 만듭니다. 이번에는 시탄유 2건이 여기에 해당해 시설 이용 경험 분모에서 제외됐습니다.

### 3.3 시설 관련 여부와 실제 이용 여부를 분리합니다

시설 이름이 포함된 리뷰라고 모두 시설 이용 경험은 아닙니다.

- 방문했지만 입욕하지 않음
- 외관만 봄
- 대기 때문에 포기함
- 숙박 이용 중 부속 욕장만 이용함
- 식당·휴게실·수영장만 이용함

이런 행은 원장에는 남기되 시설 판정 분모와 분리합니다. `facility_related=true`만으로 실제 입욕을 가정하지 않습니다.

숙박 부속 당일입욕 시설은 다음 세 수를 반드시 따로 집계합니다.

- `dayuse_only_direct_reviews`
- `lodging_bath_only_direct_reviews`
- 입욕하지 않은 시설 맥락 리뷰

### 3.4 최종 QA 스키마를 지역마다 동일하게 사용합니다

간사이권 QA에는 규슈 QA에 있던 플랫폼 수와 계약 상태 필드가 빠져 후처리에서 원장을 다시 계산해야 했습니다. 다음 필드는 모든 지역의 최종 QA에 포함합니다.

- `direct_body_platform_count`
- `korean_full_body_direct_reviews`
- `latest_stratum_seen`
- `low_rating_stratum_seen`
- `official_water_profile_status`
- `review_signal_contract_status`
- `forbidden_review_signal_rows`
- `forbidden_review_tags`
- `legacy_water_method_fields`
- `invalid_review_signal_rows`

## 4. 판정으로 이어지는 리뷰 수집법

### 4.1 시설 전체 표본과 항목 표본을 함께 봅니다

시설 판정 공개 조건은 다음과 같습니다.

- `full`: 시설 관련 직접 이용 경험 300건 이상, 직접 본문 플랫폼 3개 이상, 공개 가능한 항목 3개 이상
- `lite`: 시설 관련 직접 이용 경험 50건 이상, 직접 본문 플랫폼 2개 이상, 공개 가능한 항목 2개
- 공개 항목: 독립 이용 경험 5건 또는 10건 이상, 전체 분모의 2% 이상, 2개 이상 플랫폼

따라서 전체 리뷰 수만 채우고 끝내면 안 됩니다. 같은 핵심 항목이 최소 2개 플랫폼에서 확인되도록 수집합니다.

예를 들어 혼잡 20건이 모두 Google에만 있으면 판정 근거로 공개할 수 없습니다. Google 15건과 Nifty 5건처럼 플랫폼이 나뉘어야 합니다.

### 4.2 `mention_count`와 `source_count`를 구분합니다

- `mention_count`: 같은 이용 경험 안의 반복 표현을 포함할 수 있는 원시 언급 수
- `source_count`: 중복 제거된 독립 이용 경험 수
- 사용자 판정의 `mentions`: `source_count` 사용

한 리뷰에서 "뜨겁다"를 세 번 말해도 독립 이용 경험은 1건입니다. 수집 에이전트는 signal rows를 만들 때 두 값을 모두 기록해야 합니다.

### 4.3 낮은 평점은 운영 마찰을 찾는 층위입니다

저평점 수집은 시설 전체를 부정적으로 평가하기 위한 작업이 아닙니다. 다음 조건을 구조화하기 위해 읽습니다.

- 혼잡·대기
- 접수 마감과 번호표
- 예약 방식
- 현금·결제
- 비품·샤워·수건
- 주차·계단·교통
- 운영 변경
- 관광 기대와 실제 목욕 범위의 차이

최신 층위와 저평점 층위가 모두 없으면 수량 기준을 채워도 등급을 낮출 수 있습니다.

## 5. 감촉과 색 수집 규칙

### 5.1 `water_texture`를 넓게 태깅하지 않습니다

이번 QA에서는 `water_texture` 행에 뜨거움, 계단, 현지 분위기 같은 다른 경험이 섞인 사례가 있었습니다. 다음부터 `water_texture`는 물에 몸을 담갔을 때의 촉감 표현만 포함합니다.

`water_texture` 예시:

- `ぬるぬる`, `すべすべ`, `とろとろ`
- 미끌미끌함, 매끈함, 부드러운 물감
- 염분감이나 탄산 자극처럼 물 자체의 체감

다른 신호로 보내야 하는 예시:

| 표현 | signal_type |
| --- | --- |
| 뜨겁다, 미지근하다 | `temperature_experience` |
| 계단, 주차, 역에서 멂 | `accessibility` |
| 현지인 중심, 로컬 분위기 | `local_user_culture` |
| 모래찜질의 압박감·열감 | `sand_or_steam_experience` |
| 염소·소독 냄새 | `chlorine_smell` |
| 온천다운 느낌이 약함 | `weak_onsen_feeling` |

### 5.2 감촉 subtype을 구조화합니다

현재 `signal_type=water_texture`만으로는 미끌미끌, 염분감, 유황감, 탄산감을 구분할 수 없습니다. 다음 수집 산출물에는 최소한 evidence note 또는 별도 구조 필드로 아래 코드를 남깁니다.

- `slippery`
- `salt_warmth`
- `sulfur`
- `carbonated`

코드별로 `source_count`, `platform_count`, 시설 영역을 다시 계산할 수 있어야 합니다. 자유 문장 요약만 남기면 감촉 필터로 정규화할 수 없습니다.

### 5.3 색은 감촉과 별도 수집합니다

다음 수집부터 색 표현을 별도 태그로 보존합니다.

- `white`
- `brown`
- `clear`
- `green`
- `other`
- `unclear`

후기 색 표현은 보조 카운트입니다. 사용자 필터의 `백탁`, `갈색빛`은 공식 텍스트 또는 공식 사진과 욕장 범위가 확인될 때만 공개합니다.

## 6. 공식 사실 수집 규칙

### 6.1 시설마다 같은 기본 항목을 확인합니다

공식 필터 사실 21건이 2개 시설에만 집중됐습니다. 다음 수집부터 모든 시설에서 아래 항목을 같은 순서로 확인합니다.

- 당일입욕 가능 범위
- 실내탕·노천탕·가족탕·대절탕·모래탕·증기탕
- 사우나·암반욕·휴게 공간
- 예약·번호표·접수 마감
- 요금과 별도 상품 요금
- 정기휴일과 운영 변동 공지
- 문신·연령·성별 이용 조건
- 결제수단
- 주차·셔틀·대중교통
- 공식 수질·분석표·온천수 운용

찾지 못한 항목은 추론하지 않습니다. 확인한 공식 페이지 URL과 함께 `not_found_in_checked_official_sources`로 남깁니다.

### 6.2 한 사실마다 원문·범위·날짜를 붙입니다

공식 사실 한 행에는 다음 네 요소가 필요합니다.

1. 짧은 공식 원문
2. 공식 URL
3. 확인일
4. 적용 시설 영역 또는 상품 범위

니프티온천의 필터와 태그는 공식 페이지를 찾는 후보로는 유용하지만, 단독으로 `ready` 공식 사실을 만들지 않습니다.

### 6.3 온천수 방식은 욕장 단위로 확인합니다

이번 수질 사실 16건 가운데 바로 방식 배지로 공개할 수 있는 건은 없었습니다.

- `kakenagashi_pure`: `源泉100%かけ流し` 또는 무가수·무가온·무순환을 공식 원문에서 확인
- `kakenagashi`: `源泉かけ流し` 또는 `かけ流し`를 공식 원문에서 확인
- `junkan`: `循環ろ過` 또는 `循環式`을 공식 원문에서 확인
- `天然温泉`, `100%天然温泉`, `100%源泉`: 방식 배지 근거가 아님

방식 후보를 수집할 때는 `water_system`만 적지 않고 `scope`, `kasui`, `kaon`, `disinfection`, `official_original_text`, `official_source_url`을 함께 채웁니다.

시설 전체와 특정 탕의 운용이 다르면 시설 전체 배지를 만들지 않습니다. 특정 탕 이름을 `scope_key`로 분리합니다.

- [ ] `content_type`, `direct_body_status`, boolean 값이 표준값인가?
- [ ] 실제 입욕하지 않은 행을 분모에서 분리했는가?

## 9. 수집 에이전트 전달용 짧은 브리핑
